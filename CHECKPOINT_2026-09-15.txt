2. WHAT WE DISCOVERED -- NETWORK
================================================================================

2.1  The DVL is NOT at the factory address.
     Expected 192.168.2.95, actually answers at 192.168.2.128.
     Found by sweeping the subnet; confirmed by its web UI ("Water Linked DVL
     GUI") and TCP 16171 being open.

2.2  BlueOS PUSHES MAVLink and video to a hardcoded 192.168.2.1.
     Queried from BlueOS itself:
       GET /ardupilot-manager/v1.0/endpoints/
         GCS Client Link   udpout  192.168.2.1:14550   enabled=True
       GET /mavlink-camera-manager/streams
         endpoints: ["udp://192.168.2.1:5600"], H264 1920x1080@30, running
     DHCP from BlueOS had given this laptop 192.168.2.135, so both streams were
     going nowhere. The DVL was unaffected because the container dials OUT to
     it over TCP.

2.3  The "dial out instead" workaround does NOT work.
     Tested `ros2 launch ... rov_ip:=192.168.2.2` (selects
     udpout:192.168.2.2:14550). No heartbeat, three attempts. So holding
     192.168.2.1 on the topside NIC is currently mandatory.

2.4  `sudo ip addr add` is NOT good enough.
     The address silently disappeared mid-session (NetworkManager reapplied its
     DHCP-only profile). Symptom: IMU and camera went completely dead while the
     DVL kept working normally. Very easy to misdiagnose as a code fault.
     The durable form is `nmcli con mod <profile> +ipv4.addresses 192.168.2.1/24`.

2.5  This laptop had no Ethernet port at all at the start of the session; a USB
     Ethernet adapter was required (RTL8153).

3. WHAT WE DISCOVERED -- CODE  (3 bugs, all fixed)
================================================================================

BUG 1 -- Dockerfile: image cannot build.  [blocks everyone]
  Symptom: Step 17/21, colcon build dies with
           PermissionError: [Errno 13] Permission denied: 'log'
  Cause:   `COPY --chown=$UID:$GID ros2_ws/src .../ros2_ws/src` sets ownership
           on src only. Docker creates the implicit PARENT ros2_ws as root:root,
           so the unprivileged user cannot create build/ install/ log/.
  Fix:     RUN chown $UID:$GID /home/$USERNAME/ros2_ws   (before USER switch)

BUG 2 -- imu_node.py:143: node never starts.  [blocks everyone]
  Symptom: AttributeError: 'ClockOffsetEstimator' object has no attribute
           'handle', thrown from create_timer(); node respawn-loops forever.
  Cause:   `self._clock = ClockOffsetEstimator(...)` shadows the attribute
           rclpy.node.Node uses internally for its own Clock.
  Fix:     renamed to self._clock_sync (4 references).
  Note:    the 60 unit tests cannot catch this -- they exercise
           ClockOffsetEstimator standalone, with no ROS node.

BUG 3a -- camera_node.py: segfault on startup.
  Symptom: process dies instantly with SIGSEGV, no Python traceback, no log
           output whatsoever.
  Cause:   importing gi/GStreamer AFTER rclpy corrupts the next Node()
           construction inside the _rclpy C extension.
           Verified both directions: gi-then-rclpy works, rclpy-then-gi crashes.
  Fix:     moved the GStreamer import block above the rclpy imports.
  Found with: PYTHONFAULTHANDLER=1, which produced the stack that plain stderr
           did not.

BUG 3b -- camera_node.py: 1 fps instead of 30.
  Symptom: node logs "camera 1.0 fps" while the stream is 30 fps.
  Cause:   `image.data = frame.tobytes()`. rosidl's generated setter has ONE
           fast path, array.array('B'). Anything else falls into
           `all(isinstance(v, int) for v in value)` over every byte.
           Measured: 322 ms for one 1080p BGR frame = a 3 fps hard ceiling.
  Fix:     image.data = array.array('B', frame.tobytes())
           Same fix applied to the CompressedImage publisher.
           Benchmarked: 321.24 ms -> 3.37 ms, ~95x, byte-identical output.
  Result:  1.0 fps -> 32.0 fps.

4.7  Foxglove bridge (Stage 6) -- WORKS.
     Earlier in the session it failed with "Failed to bind port: Address
     already in use". That was NOT a bug in the stack: a stale foxglove_bridge
     left over from our own earlier test run was still holding :8765. After
     `docker compose restart bluerov2` it starts correctly.

       $ ss -ltnp | grep 8765
       LISTEN 0 128 0.0.0.0:8765 users:(("foxglove_bridge",pid=37895,fd=25))

     It advertises all 17 channels (imu/*, dvl/*, camera/*).

     Websocket handshake tested directly against the bridge:
       subprotocol 'foxglove.websocket.v1' -> HTTP/1.1 400 Bad Request
       subprotocol 'foxglove.sdk.v1'       -> HTTP/1.1 101 Switching Protocols
         first message op = serverInfo
         capabilities = [connectionGraph, parameters, parametersSubscribe,
                         services, assets]
         supportedEncodings = [cdr, json]

     IMPORTANT: this foxglove_bridge build (3.5.0, Humble) speaks ONLY the
     newer subprotocol `foxglove.sdk.v1`. A Foxglove client that knows only
     the older `foxglove.websocket.v1` is rejected with 400 Bad Request and
     simply appears "unable to connect".

     Note: `capabilities` correctly does NOT include clientPublish, so nothing
     in this stack can be commanded from the visualisation tool. That matches
     the author's stated intent.

     The client on this laptop is Foxglove Studio 2.51.0, installed from
     foxglove-studio-latest-linux-amd64.deb into /opt/Foxglove.
     It DOES support the required subprotocol -- both strings are present in
     /opt/Foxglove/resources/app.asar -- so NO UPDATE IS NEEDED on this
     machine. On a different laptop with an older Studio, an update would be
     the fix rather than touching the bridge.

     To connect:  ws://localhost:8765
                  ws://<this-laptop-ip>:8765   from another machine
     Must be ws://, not http://. The container uses host networking, so no
     port mapping is involved.

     VISUAL CHECK DONE: layout imported, connected, topics visible and the
     camera frame renders. Stage 6 is complete.

     GOTCHA found during that check -- the shipped layout cannot work on a
     first import. config/foxglove_layout.json binds the Image panel to a
     calibration topic:
         "imageTopic":       "/bluerov2/camera/image_raw/compressed"
         "calibrationTopic": "/bluerov2/camera/camera_info"
     but config/camera_info.yaml is deliberately a placeholder with all-zero
     intrinsics, so Foxglove reports "invalid focal length" and refuses to
     render the image. Both files are individually correct; together they
     contradict each other.
     Workaround used (no file changed): in the Image panel settings sidebar,
     set Calibration to None. Adding a fresh Image panel also works, since a
     new panel starts with no calibration bound.
     Permanent fix, once someone decides: either drop "calibrationTopic" from
     the layout, or ship a real calibration. NOT changed - deliberately left
     as-is, since this session was about connections, not calibration.

7. ODDITIES -- worked, but looked wrong
================================================================================

7.1  |a| = 10.26 m/s2 at rest, 4.5% above 9.81. The driver's MAVLink scaling
     constants were checked and are correct per spec, so this points at an
     uncalibrated accelerometer. Run the ArduSub accel calibration.

7.2  |B| = 21 uT. Italy should be roughly 47 uT. Suggests the magnetometer
     needs calibrating in ArduSub. Would show up as a constant heading offset.

7.3  IMU temperature 59.5 C. Plausible for electronics in a sealed enclosure,
     but worth a look.

7.4  DVL dead reckoning reports positions of hundreds of km with a std of
     ~8e6 m. Consistent with never having had bottom lock, but MUST be
     re-checked in water before any SLAM consumes that topic.

7.5  The DVL's internal clock is about 2 years slow (reports 2024-05-27).
     Harmless as things stand: dvl_node.py:250 stamps on arrival from the ROS
     clock and carries the instrument times only as separate fields. Would be
     confusing in a bag file.

7.6  MAVLink heartbeat is reported as "system 0, component 0, autopilot type 8".
     Type 8 is MAV_AUTOPILOT_INVALID, which is what a ground station sends
     rather than an autopilot. Data flows correctly at full rate, so this is
     cosmetic, but the driver is arguably latching onto the wrong heartbeat.

7.7  UNDIAGNOSED: a separate Python process subscribing to raw /camera/image_raw
     reads only ~3 fps, while the node publishes at 32 fps (its own counter, and
     camera_info from the same callback measures 32 Hz at that same external
     subscriber). Enabling shared memory changed nothing. This was NOT resolved.
     It matters if the VSLAM front end runs as a separate process from the
     driver - which for a VSLAM stack it probably will.

  docker compose exec bluerov2 bash -lc 'ros2 topic list'
  docker compose exec bluerov2 bash -lc 'ros2 topic hz /bluerov2/imu/data_raw'

    'ros2 topic echo /bluerov2/imu/data_raw --field linear_acceleration --once'

  launch first. Stale nodes cause identical symptoms;
  `docker compose restart bluerov2` clears them.
